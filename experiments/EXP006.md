# EXP006 — Scale the fixed EXP003 supervised reranker

Status: **implementation only; AWS smoke pending**. No Amazon TRAIN/TEST data or
indexes are present in this worktree. No measured EXP006 gain or runtime is claimed.

## Question and frozen controls

EXP003 fitted HistGradientBoosting (HGB) on 5,999 original FIT S1 entities. EXP006
tests whether adding **50,000 independently sampled TRAIN S1** improves its held-out
macro F0.5. The candidate generator remains the frozen compact_18 pass-eligible
pool before the old total-60/source cap. The 51 `FEATURE_NAMES`, per-entity
negative sampler, index readers, HGB factory and TEST inference implementation
are unchanged. No external data or TEST labels are used.

The original 20,000-S1 universe is hash-pinned to
`84fa2544c2905fa480ffc0e57a2912143304acb6653a5f6c09a3eefa2a66979c`.
Its 5,999 FIT, 2,001 TUNE and 12,000 EVALUATION IDs are reconstructed using the
same country × singleton stratifier and seed 2029. `preflight` compares them with
the original `partitions.csv` and checks FIT/TUNE pair-cache checksums. Held-out
EVALUATION files are checksum-verified only after the frozen bundle is validated.
EXTRA_FIT excludes **all** 20,000 IDs, not only original FIT. Sampling checks
zero overlap and records that assertion in its manifest. FIT consumes only
original `pairs/fit` plus merged EXTRA_FIT pairs. TUNE consumes only original
`pairs/tune`; EVALUATION consumes only original `pairs/evaluation` after freeze.

## Sampling and pair generation

`sample` makes two streaming passes over TRAIN S1. It counts eligible S1 by
country, allocates exact country quotas by largest remainder, and selects the
lowest stable BLAKE2b keys within each country using seed 2032. This uses no
ground-truth counts to choose IDs. Sizes including 10k, 25k, 50k and 100k are
supported, but only **50k** is accepted by the primary `fit` command. The
manifest records seed, requested/actual size, full source and truth hashes,
file identities, exclusion hash, country counts, and zero-overlap checks.

Each `generate` worker assigns sorted sample positions modulo shard count
(default 4). It opens existing TRAIN S2/S3 indexes read-only. For each S1 it
retrieves compact_18 raw and pass-eligible candidates, labels only retrieved
pairs, retains all eligible positives, and applies EXP003's exact per-entity
sampler: up to 20 hardest negatives plus up to 3 nonduplicate easy negatives,
seed 2031. The hardness formula is `0.7 * exp001_rule_score + 0.3 *
min(best_retrieval_score, 100)`. Positive pairs outside the eligible pool are
diagnosed as blocking misses; none are injected.

Each worker commits entity rows into a local SQLite checkpoint every 100 S1
(or the requested interval). A worker lock prevents simultaneous writes to one
shard. Resume validates sample, source/index identity, shard count, positions,
IDs and committed rows, then continues after the last committed entity. A
completed shard has a deterministic row-content SHA256; changing its data or
identity fails closed. Interrupted transactions may repeat up to 99 entities.
`merge` requires every completed shard, validates all row hashes, and writes
one deterministic `.f32` feature matrix, pair TSV and per-entity diagnostic CSV
in sorted S1 order. The merged manifest hashes all artifacts. A fresh output
directory is required for merge and every later stage.

The merge summary reports raw and eligible candidate recall, retained positive
and negative counts, and average raw and eligible candidates per S1. Its
`pool_counts.csv` retains S1 country and per-entity counts. The original 20k
pool diagnostics remain in the EXP003 cache.

## Fixed fit, threshold and promotion

The first HGB uses the exact EXP003 winner: learning rate 0.08, 160 iterations,
31 max leaf nodes, 30 minimum samples/leaf, L2 1.0, balanced class weights,
seed 2030 and `early_stopping=False`. The model and its full configuration are
written before TUNE. There is no model search or pair-level split. The 50k
sample is the primary configuration; optional scale ablations are not launched
by this command.

`tune` loads only the unchanged 2,001-S1 TUNE truth and eligible pair cache. It
searches the EXP003 probability grid plus thresholds 0.500–1.000 at 0.001
increments, maximizing exact macro F0.5; ties choose the higher threshold. It
saves the model bundle, threshold grid and freeze manifest before EVALUATION.
`evaluate` verifies those hashes first, then reads the original 12,000-S1
EVALUATION truth exactly once to create a new output directory. It writes
overall, country, source, source×country and multiplicity slices using EXP003's
metric code, including TP/FP/FN, blocking/matcher FN, singleton accuracy and
mean predictions/S1.

Baseline EXP003 EVALUATION F0.5 is **0.905874** (precision 0.936684, recall
0.848791). Promotion requires zero leakage, exact feature/blocker compatibility,
TUNE-only threshold, a frozen EVALUATION run, and F0.5 **strictly greater than
0.905874**. A result at or below baseline is **NO PROMOTION**. From 0.9059 to
0.910 is weak; at least 0.910 is interesting, at least 0.915 is a strong
candidate, and at least 0.925 is major. Completing training alone is no evidence
of improvement. No TEST inference is part of EXP006's local verification.

## AWS commands (4 vCPU, 16 GiB; run from repository root)

Use the existing pinned environment and the **TRAIN** index path already used
by EXP003. These commands assume `results/exp003_20k` contains the original
completed `pairs` cache and `partitions.csv`.

### A. Preflight

```bash
python scripts/run_exp006.py preflight \
  --train-dir data/raw/train \
  --index-dir results/artifacts/exp002c_source_index \
  --original-dir results/exp003_20k
```

### B. 5k EXTRA_FIT, four-shard runtime smoke

```bash
python scripts/run_exp006.py sample --train-dir data/raw/train \
  --size 5000 --sample-dir results/exp006_smoke_5k_sample
for shard in 0 1 2 3; do
  /usr/bin/time -p python -u scripts/run_exp006.py generate \
    --train-dir data/raw/train \
    --index-dir results/artifacts/exp002c_source_index \
    --sample-dir results/exp006_smoke_5k_sample \
    --shard-dir results/exp006_smoke_5k_shards \
    --shards 4 --shard "$shard" \
    > "results/exp006_smoke_5k_shard_${shard}.log" 2>&1 &
done
wait
python scripts/run_exp006.py merge --train-dir data/raw/train \
  --index-dir results/artifacts/exp002c_source_index \
  --sample-dir results/exp006_smoke_5k_sample \
  --shard-dir results/exp006_smoke_5k_shards --shards 4 \
  --output-dir results/exp006_smoke_5k_merged
```

Inspect all four `done.json` files and logs after `wait`: shell `wait` for a
bare set of background jobs does not by itself prove all four succeeded. To
resume an interrupted shard, rerun its identical `generate` command with the
same paths, shard count, and shard number.

**Runtime estimate is pending smoke measurement.** After the smoke, use the
largest measured per-shard wall time (including index and source scans) as the
four-worker smoke wall time. A first planning projection for 50k is `10 ×`
that observed wall time; report it as a projection, not a measured 50k run.
Check disk headroom and RSS from the smoke before starting 50k.

## Operational limits

Four workers each independently scan TRAIN S1 and ground truth and open the
same existing read-only S2/S3 indexes. Every resumed stage checks full TRAIN
S1 and truth hashes against the sampling manifest. The existing index reader
uses source/index size and modification time, consistent with EXP003; preserve
timestamps when moving indexes and data. SQLite checkpoints and merged matrices
need ample free disk.
The 16 GiB host has not yet been profiled with 50k. If the smoke shows memory
or disk pressure, stop before 50k and investigate; do not change blocker,
features or HGB configuration within this primary experiment.
