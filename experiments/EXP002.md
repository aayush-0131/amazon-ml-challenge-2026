# EXP002 — Higher-Recall Blocking and Learned Matching

## Objective

Improve substantially over EXP001 by:

1. increasing true-link blocking recall;
2. retaining bounded candidate sets;
3. replacing the hand-written matching rule with a learned pair matcher;
4. preserving full-test scalability.

EXP001 reference:

- positive-link blocking recall: 86.419%
- held-out macro F0.5: 0.627204
- mean candidates/S1: 49.407

## EXP002b — Persistent SQLite FTS5 Blocker

Implementation checkpoint:

`9647cbf feat: add indexed blocker for EXP002`

### Architecture

Separate persisted indexes were created for S2 and S3 containing:

- source records;
- normalized exact-name lookup;
- normalized exact-address lookup;
- normalized name-signature lookup;
- SQLite FTS5 name/address documents;
- FTS vocabulary statistics.

Production queries do not rescan the source TSV files.

### Runtime diagnosis

The query process remained CPU-bound at approximately 100% CPU.

Observed during the run:

- process RSS approximately 419 MiB
- no swap activity
- no major page faults
- target SQLite indexes remained resident/cache-served
- approximately 1.69 TB of logical reads were observed during the diagnostic

The primary bottleneck is therefore query execution rather than memory pressure
or raw EBS throughput.

The indexed implementation performs multiple per-token FTS queries using
`ORDER BY bm25(...)`, potentially many times for every S1/source pair.

The benchmark also used `SourceIndexConfig()` defaults whose token-DF limits are
substantially larger than the stricter limits recorded in the EXP002 JSON
configuration.

### Decision

**REJECT EXP002b as a production blocker.**

Reasons:

1. recall (81.723%) is lower than EXP001 blocking recall (86.419%);
2. mean candidate count increased to approximately 199/S1;
3. candidate budget is saturated at 200 for nearly every S1 entity;
4. 5k retrieval requires approximately 5,030 seconds;
5. scaling this implementation to full TEST is infeasible.

Do not run the 20k benchmark.
Do not activate the learned matcher yet.

## EXP002c — Country-scoped explicit postings (implementation)

Branch: `feat/exp002c-fast-postings`.
Commit: the commit containing this section (`git log -1 --format=%H -- configs/exp002c_postings.json`).
Status: implementation ready for AWS 1k/5k verification; **no EXP002c full-data
build, recall, runtime or RAM result has been measured yet**. EXP002b measurements
above remain historical evidence, not estimates for this implementation.

### Architecture and limits

Each source has a separate SQLite schema-2 database with a `WITHOUT ROWID`
posting table keyed by `(country, field, token, record_id)`. Distinct normalized
name/address tokens are persisted once per record. `token_df` stores counts
per raw country/field/token; `country_counts` avoids source scans for IDF.
The normalization is shared with query code (NFKC/casefold/punctuation-to-space);
there is no separate FTS tokenizer or accent-stripping behavior.

Queries first use exact normalized-name, exact normalized-address and sorted
name-token-signature indexes. They then expand complete rare-token posting lists,
with country-scoped DF limits 60/40/250 for name/address/numeric retrieval and
4/4/3 eligible terms respectively. These are explicitly chosen **source-side**
limits, not an automatic statistical conversion of EXP002a query-side DF.

Up to 8 informative terms across name and address also supply at most 10
two-token intersections. A left anchor may have at most 5,000 postings; an
indexed primary-key probe tests membership in the other list. This permits
common name+name or name+numeric/address evidence without expanding the entire
common posting list. An intersection over 150 hits is rejected in full and
reported; it is not truncated into an arbitrary single-token top-N result.
All candidate IDs are deduplicated before fetching record text in batches of
400 and scoring. Exact results have a deterministic 250-hit safety bound with
overflow instrumentation. Raw country strings remain equal in every pass.

`configs/exp002c_postings.json` is the authoritative retrieval configuration.
Every `SourceIndexConfig` key is required; missing or unknown keys raise an
error. Passing the old EXP002 config is an error rather than silently using
defaults. The initial final budget is 40/source (80/S1 maximum), with deterministic
per-pass ranks/scores, no character pass, and no learned matcher. This smaller
cap is a resource bound, **not evidence that recall or saturation gates pass**.

The old FTS databases are kept intact. New filenames are
`exp002c_s2_postings_v2.sqlite` and `exp002c_s3_postings_v2.sqlite`.
Schema 1 is rejected if explicitly opened. Builds reserve a `.building.sqlite`
file exclusively and leave failed partial files for inspection. A successful
build checks SQLite integrity and atomically replaces the destination; a failed
rebuild retains the prior complete database. Reuse validates the raw file size
and mtime fingerprint (not a cryptographic content check). Querying uses only
the persisted indexes; target TSVs are never scanned per S1 or query batch.

Build buffers are limited to 10,000 source rows, with a 128 MiB SQLite cache
and file-backed temporary storage. Readers use 32 MiB caches per source and
per-query DF/weight caches. Disk size/build throughput may be worse than FTS5
because explicit postings repeat keys; those costs require AWS measurement.

### Diagnostics and verification

Synthetic tests cover country-scoped distinct DF, rare posting expansion,
common and cross-field intersections, numeric provenance, overflow handling,
exact passes, deterministic ordering, config validation, schema rejection,
atomic failed rebuilds, fingerprint checking, cap behavior, and complete
build-only/query-only benchmark invocation including singleton/multi-match
recall. Local validation: `.venv/bin/python -m pytest -q` — **41 passed**.
No Amazon-data index build or benchmark was run in Codex for EXP002c.

The benchmark records per-source and country/source-slice timings, time/S1,
exact/token/extra-token candidate contributions, raw pool size, cap-hit and
cap-truncation rates, posting-list lookups, intersection overflows, recall before
the cap and final recall. Cap rates use S1/source queries as denominator; token
and exact contribution sets overlap, while token-only counts exclude exact hits.
Peak RSS is cumulative process RSS; running build and queries in separate
processes separates their memory measurements. Sample IDs, config and commit
manifest are persisted. Seeds/IDs use the same nested hash samples as EXP002b
(seed 2032). The 5k run may benefit from the 1k run's OS cache warming.

### Pending AWS gate

Goal:

Retain persistent source-side indexing while replacing repeated FTS/BM25
per-token retrieval with fast explicit token-postings lookup.

Required properties:

- country-scoped postings;
- country-scoped token document frequencies;
- exact name/address/signature retrieval retained;
- rare informative token retrieval;
- bounded posting-list expansion;
- multi-token intersection/union where useful;
- no per-token BM25 query explosion;
- deterministic candidate provenance;
- bounded memory;
- benchmark 1k and 5k before 20k;
- learned matcher remains blocked until retrieval passes.

Target retrieval gate:

- positive-link recall >= 96%, stretch >= 98%;
- materially better all-links-retained rate than EXP001;
- candidate set ideally <= 80/S1 average;
- practical projected full-test runtime.

Require no near-universal cap saturation. The strict DF limits, intersection
anchor/overflow limits, exact-hit cap and final 40/source cap may still lose
true links; use the recorded diagnostics to assess them. No performance or
recall success is claimed before AWS results. Learned matching and 20k remain
blocked until this gate is reviewed.
