### Architecture and limits

Each source has a separate SQLite schema-2 database with a `WITHOUT ROWID`
posting table keyed by `(country, field, token, record_id)`. Distinct normalized
name/address tokens are persisted once per record. `token_df` stores counts
per raw country/field/token; `country_counts` avoids source scans for IDF.
The normalization is shared with query code (NFKC/casefold/punctuation-to-space);
there is no separate FTS tokenizer or accent-stripping behavior.

Queries first use exact normalized-name, exact normalized-address and sorted
name-token-signature indexes. They then expand complete rare-token posting lists,
with country-scoped DF limits 60/40/250 for name/address/numeric retrieval and
4/4/3 eligible terms respectively. These are explicitly chosen **source-side**
limits, not an automatic statistical conversion of EXP002a query-side DF.

Up to 8 informative terms across name and address also supply at most 10
two-token intersections. A left anchor may have at most 5,000 postings; an
indexed primary-key probe tests membership in the other list. This permits
common name+name or name+numeric/address evidence without expanding the entire
common posting list. An intersection over 150 hits is rejected in full and
reported; it is not truncated into an arbitrary single-token top-N result.
All candidate IDs are deduplicated before fetching record text in batches of
400 and scoring. Exact results have a deterministic 250-hit safety bound with
overflow instrumentation. Raw country strings remain equal in every pass.

`configs/exp002c_postings.json` is the authoritative retrieval configuration.
Every `SourceIndexConfig` key is required; missing or unknown keys raise an
error. Passing the old EXP002 config is an error rather than silently using
defaults. The initial final budget is 40/source (80/S1 maximum), with deterministic
per-pass ranks/scores, no character pass, and no learned matcher. This smaller
cap is a resource bound, **not evidence that recall or saturation gates pass**.

The old FTS databases are kept intact. New filenames are
`exp002c_s2_postings_v2.sqlite` and `exp002c_s3_postings_v2.sqlite`.
Schema 1 is rejected if explicitly opened. Builds reserve a `.building.sqlite`
file exclusively and leave failed partial files for inspection. A successful
build checks SQLite integrity and atomically replaces the destination; a failed
rebuild retains the prior complete database. Reuse validates the raw file size
and mtime fingerprint (not a cryptographic content check). Querying uses only
the persisted indexes; target TSVs are never scanned per S1 or query batch.

Build buffers are limited to 10,000 source rows, with a 128 MiB SQLite cache
and file-backed temporary storage. Readers use 32 MiB caches per source and
per-query DF/weight caches. Disk size/build throughput may be worse than FTS5
because explicit postings repeat keys; those costs require AWS measurement.

## EXP002e — Selective intersection retrieval (implementation only)

Branch: `feat/exp002e-selective-intersections`. Implementation commit:
`git log -1 --format=%H -- src/business_entity_resolution/intersection_scheduler.py`.

### Algorithm and compatibility

`selective_v1` is explicitly selected in each new config; omitted strategy
defaults to `legacy`. `configs/exp002c_postings.json` is unchanged. Legacy term
prefix, pair ordering, early break, scoring, pass ranks and candidate selection
remain unchanged, tested against a frozen EXP002c implementation. Storage,
index filenames and schema version remain **2**. Existing indexes open read-only
and remain byte-for-byte reusable; no migration/build is involved. EXP002d's
legacy intersection-reason classifier refuses selective configs rather than
silently applying the wrong ordering assumptions.

For each S1/source, use only query tokens and country-scoped DF/population:

1. Sort positive-DF usable terms by `(DF, field, token)`. Reserve the rarest
   available name, nonnumeric-address and numeric-address term, then fill by DF
   up to 16 terms. Numeric classification uses Unicode `isdecimal()`, not an
   India/US rule. Raw country equality and all exact passes remain unchanged.
2. Enumerate at most 120 pairs in Python. Orient the smaller posting as anchor.
   Reject anchor DF >50,000. Above ordinary anchor DF 5,000, require
   `DF_left * DF_right <= 150 * country_population`. The independence proxy is
   a heuristic, not a promised intersection size. Smaller anchors retain their
   original cost bound without this additional gate.
3. Greedily choose up to 24 pairs, at most 6 probes involving any one term.
   Order by `(maximum endpoint usage, total endpoint usage, pair-kind usage,
   DF product, left term, right term)`. This balances term coverage first,
   same/cross-field kind diversity next, and selectivity within ties. Country
   population is constant within a query, so product ranks identically to the
   normalized proxy. No labels enter planning.
4. Execute only selected pairs using the existing indexed CROSS JOIN membership
   probes and `LIMIT 151`. Reject the entire intersection if >150 hits; never
   retain an arbitrary overflow prefix. Deduplicate before batched record fetch
   and unchanged lexical scoring/ranking. Preserve name/address/numeric pass
   provenance. Optional trace records sorted terms, ordered pairs, bounded hit
   counts, proxy, overflow and sorted contributed record IDs (empty on overflow).

The 16/24/6 bounds expand coverage beyond legacy 8/10 without issuing SQL for
every combination. Reserving token kinds avoids a long name excluding all
address evidence. The larger anchor allowance targets EXP002d's anchor misses,
but remains bounded and selectively gated. These are hypotheses to benchmark,
not established optimal values.

### Diagnostics and risks

Benchmark CSVs retain all prior recall, pre-cap recall, matched-all retention,
candidate-count quantiles, cap-hit/truncation, runtime/projection and open-country
slices. Added diagnostics: Python pairs considered; anchor/selectivity skips;
term-quota removals encountered before planning stops; actual SQL probes;
overflow/nonempty-success counts; unique candidate IDs added beyond exact and
single-token passes; SQL and total intersection seconds; scheduler version.
Mean/p95 probe counts explicitly use the S1/source-query denominator. Existing
`average_*_per_s1` counters sum both sources for overall/country slices.
Candidate uniqueness is within one source query, not across the whole dataset.
SQL timing includes result materialization; total intersection time also includes
DF lookup and Python planning. Timings naturally vary; deterministic scheduling
and candidates do not. Peak RSS is the process high-water mark, not incremental
query memory. Index-build CSV reports reuse/zero build seconds, not a new build.

Correlated/generic tokens can defeat the independence proxy. Worst-case selected
anchor work can approach 24 * 50,000 indexed membership probes per S1/source;
overflow short-circuiting is not guaranteed to save low-hit probes. Intersections
alone can contribute up to 24 * 150 raw candidates before deduplication, plus
bounded singleton/exact expansion. Moderate/balanced variants also increase
single-token scoring work. Per-pass rank 40 and total 60 may still reject true
links. Bounded memory is not proof of practical runtime; measure CPU/RAM and
all source/country slices at 1k before authorizing 5k. The gate remains final
recall >=96% (stretch 98%), improved all-links retention, ideally <=80 mean
candidates/S1, improved India/S3 India, and practical projected full-test time.

### Exact algorithm: selective_v2_compact

Retain v1's 16-term pool, including reserved rare name/address/numeric terms;
enumerate at most 120 combinations in Python using country-scoped DF.
Orient the smaller posting as anchor. Skip anchor DF >50,000, then apply
`DF_left * DF_right <= 150 * country_population` to **all remaining pairs**,
including anchors <=5,000. This is an independence heuristic, not a guarantee
of either selectivity or recall. Same-country/open-string and Unicode decimal
handling remain unchanged. No labels enter production scheduling.

Among eligible pairs retain v1's deterministic greedy order:
`(maximum endpoint usage, total endpoint usage, pair-kind usage, DF product,
left term, right term)`. Respect each config's maximum planned/actual probes
and per-term quota. Only bounded selected pairs execute SQL. Preserve endpoint
coverage and same-/cross-field pair-kind diversity; a stricter gate may remove
some kinds before planning. No common posting lists are fully materialized.

Execute each planned indexed intersection with `LIMIT 151`. More than 150
hits rejects the entire probe result, contributing zero IDs. Otherwise retain
the **entire** result and its provenance. Count newly contributed IDs only:
exclude all initial exact/single-token IDs and IDs already added by previous
intersections. After a completed successful probe reaches/exceeds the configured
unique-output budget, stop before the next SQL probe. Never trim a successful
result to fit the budget. Overshoot is at most 149 unique IDs (budget + 149
absolute maximum). Empty/overflow probes do not consume output budget.
Candidate ranking and per-pass/final selection are unchanged.

### Diagnostics, trace and compatibility

Each S1/source records planned pairs, actual SQL probes, separate anchor,
selectivity, term-quota and candidate-budget skips, overflow/nonempty/empty
probes, unique additions, budget-reached flag, raw/eligible/final candidates,
SQL seconds and total intersection seconds. Candidate-budget skips count planned
but unissued probes. Term-quota skips count discarded pairs encountered before
planning terminates; they do not count every unused pair after probe-limit exit.
Anchor/selectivity skips are mutually exclusive (anchor rule evaluated first).
CSV summaries report means and p95 using source-query denominators for these
fields, across overall, country, source and country/source slices. Mean of the
budget-reached flag is its rate. Prior recall/retention/cap/runtime/RSS metrics
remain available and comparable.

Optional `retrieve(..., trace=True)` exposes ordered planned probes/proxies,
actual bounded hits, overflow, contributed record IDs, each probe's new-ID count,
cumulative unique additions, budget reached, and whether later SQL was suppressed.
Trace is observational; tests compare traced/untraced candidates. A last probe
may reach the budget without suppressing any later probe: reached is then true,
stopped-by-budget false. Timing output is naturally not byte-deterministic.

### Risks and decision gate

The stricter independence proxy may remove correlated true pairs, especially
India/S3 India. Output stopping can favor early noisy intersections and suppress
useful later pairs. A whole-result overshoot can be large for compact_6 (up to
249 new IDs). Total raw volume also includes unchanged exact/single-token
retrieval; output bounds do not guarantee a low final cap-hit rate. Larger
anchors still imply up to 50,000 membership checks per probe, so a bounded probe
count does not guarantee EXP002c-level runtime. No speed/recall claim is made.
Compare pre-cap >=96%, final recall, all-links retention, intersection/raw volume,
candidate pressure, per-source timings/RSS and India/S3 India before deciding
which compact setting deserves 5k. EXP001 remains the best validated matcher.
